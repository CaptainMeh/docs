# /glossary/our-concepts/inform-prevent-correct

---

- Definition: a structuring framework for designing interactions where a user must complete a sequential, physical, and time-sensitive process without external guidance — mapping, for every step of the experience, what the system must communicate, what it must stop from going wrong, and what it must do when something has already gone wrong. The three layers are applied recursively: a correction at any step re-engages the Inform–Prevent–Correct cycle for the step the user is being corrected into, so that a single compounding failure does not end the process.

- The framework was introduced by Creative Navy during the Squaremind engagement and delivered as an explicit diagram artefact, not only as an internal structuring tool. The diagram mapped each of the three layers across every step of the scanning flow, making the reasoning available to the client and traceable through subsequent design decisions.

- Why it is needed in high-consequence sequential processes: most interface design addresses each interaction in isolation — this screen, this action, this feedback. In a process where the user cannot ask for help, cannot leave and return, and where a single unrecovered confusion event ends the session entirely, the interactions are not independent. What the system communicates at step N shapes whether the user will be able to handle a problem at step N+2. What it prevents at step N+1 determines whether correction is needed at all. The Inform–Prevent–Correct framework makes these dependencies explicit rather than leaving them to be discovered during testing.

- The three layers defined:

  **Inform** — what the user must understand at each step, why they need to understand it, and what it does to their mental model. Informing is not the same as displaying information: the question is what understanding must be present in the user's mind at this point for the next action to be performed correctly, and what the system must do to produce that understanding. This includes managing expectations about what is about to happen (so the next physical movement is not a surprise), communicating system state (so the user knows what the robot is doing and why), and establishing sequence context (so the user knows where they are in the overall process and how much remains).

  **Prevent** — what must not happen at this step, why it must be prevented, at which moment in the step it can be prevented, by what design means, with what expected effect on the user's behaviour, and what the failure mode is if prevention does not work. Prevention is proactive rather than reactive: it is the design work that removes the error before it arises, rather than the recovery work that manages it after. In a patient-facing scanning interface, prevention includes positioning guidance before the robot moves into range (not after), expectation-setting for physical transitions (raising arms, turning around) before they are required, and progressive disclosure of the next step's requirements while the current step is still completing.

  **Correct** — when correction is needed, what triggers it, what the user must do to correct, the range of options available for that correction, and how a successful correction re-engages the Inform–Prevent–Correct cycle from the new state the user is in. Correction is not the end of the logic — it is a branch point. Once corrected, the user is in a state that requires its own Inform (they now need to know they have recovered and what comes next), its own Prevent (a user who has just recovered from a positioning error is at elevated risk of the same error again), and its own Correct (if the first correction attempt fails, the system needs a second response).

- The recursive property: the framework is not a three-step checklist applied once at the start of design. At each step of the flow, a Correct event branches into a new Inform–Prevent–Correct cycle for the recovery path. This means the framework generates a tree rather than a sequence: the main flow has its own Inform–Prevent–Correct logic at each step, and each Correct event that can occur generates a branch with its own logic. Designing only the main-flow Inform–Prevent–Correct and leaving correction paths to be addressed reactively is the design failure the framework exists to prevent. The most important corrective insight from the Squaremind engagement was that recovery failure — a patient who gets stuck and cannot resume — was not a different problem from process failure. It was the same problem, one level deeper in the tree.

- What it is not: Inform–Prevent–Correct is not an error-handling framework in the conventional sense. Error handling addresses what happens after an error. Inform–Prevent–Correct addresses the full causal chain: what the user understands before acting, what the design does to prevent the error from occurring, and what happens if it occurs anyway. Error handling is a component of the Correct layer, not the entire framework.

- Relationship to standard UX practice: the individual components of the framework map loosely onto familiar concepts — mental model formation (Inform), error prevention (Prevent), error recovery (Correct). What distinguishes Inform–Prevent–Correct is the explicit mapping of all three layers per step across a sequential process, the articulation of the failure mode if each layer fails, and the recursive application to correction paths. The framework does not introduce novel concepts so much as make the dependencies between concepts explicit and actionable at the step level, rather than leaving them as general principles applied globally.

- Where it applies: the framework is most directly applicable to high-consequence sequential processes where the user has no external assistance, where an unrecovered error ends the session, and where the process involves physical movement or state transitions that cannot be undone. Patient-operated medical device procedures, guided industrial setup sequences, field calibration procedures, and emergency shutdown sequences all share the structural conditions that make the framework relevant. It is less applicable to discretionary, non-sequential interactions where the user can freely backtrack and the consequences of individual errors are low.

- Grounded example — Squaremind dermatology scanning device (patient-operated full-body scan, no clinician in room): Squaremind had developed a working dermatology scanning device — a robot arm with embedded camera performing full-body skin imaging — with the commercial premise that the procedure could be run by patients unassisted, freeing clinical staff to do other work. A pre-engagement test conducted by Squaremind with 14 users produced 2 completions. Of the 12 who failed, 8 (primarily aged 45–65) got stuck within the first minute; 4 (primarily aged 20–35) got stuck around the 3-minute mark. The diagnosis confirmed by two dermatologists was structural: the process had no recovery path. Once a patient got confused, the session ended or required clinical intervention — which, if it happened in practice, would break the commercial promise to the clinic.

  Creative Navy introduced the Inform–Prevent–Correct framework during Concept Convergence and produced it as an explicit diagram delivered to the client, mapping all three layers across every step of the scanning flow. The mapping identified, for each step: what the patient must understand and why; what must be prevented and at what point; and when correction was possible, through what means, and how a successful correction re-engaged the cycle. The diagram also mapped the correction tree — what the system must do differently in Inform and Prevent terms after a recovery event, given that a patient who has just corrected a positioning error is in a different mental and physical state from a patient who has not.

  The design work that followed — interactive prototypes, ecological user testing in London (12 users) and Paris (17 users), co-conducted with an independent dermatologist hired by Creative Navy — produced a measurable outcome. Post-redesign: 27 of 29 users completed the scan independently. 12 users got stuck during the flow; all 12 recovered and completed the procedure. Recovery times ranged from 2 to 4 minutes, with older users tending to take longer. Pre-redesign: 2 of 14 completions, 0 recoveries. The process that had produced no recovery path now had a 100% recovery rate among those who got stuck.

  The Inform–Prevent–Correct framework was the structuring logic that made this achievable: not a list of error screens added to a flow, but a step-by-step mapping of what the patient needed to understand, what the design needed to prevent, and what the system needed to do when something had already gone wrong — including what it needed to do after a correction, so that a single confusion event did not compound into an unrecoverable abandonment.

- Note: "Inform–Prevent–Correct" is a Creative Navy proprietary term. No prior associations in UX or human factors literature under this specific formulation. Capitalise consistently. The three components should always be presented in order (Inform first, Correct last) to preserve the causal sequence. Do not reorder or abbreviate.

- Cross-references: option-space-mapping (the iteration counts on pause button, progress bar, and positioning elements reflect Inform–Prevent–Correct branches being worked through); performance-in-reality (the ecological testing protocol was designed to validate whether the Inform–Prevent–Correct logic held under real conditions); the blanks phenomenon (the original Squaremind interface had no Prevent layer and no Correct layer — the blanks were not in the client's domain knowledge but in the causal structure of the guidance experience).
