# `/capabilities/state-and-status-visibility-design`

Cross-reference the provenance page in one sentence: state visibility concerns what the machine is doing; information state concerns what is known about a reading and how well it is known.

---

## Domain vocabulary

- System state / operational state / device state — the current condition of the system as relevant to the user's next action
- State visibility — the degree to which users can understand what the system is doing without active interpretation
- Glance readability / peripheral attention — state communication that holds up under brief, partial attention; not requiring the user to stop and read
- Recognition over recall (link to `/situations/complexity/operators-rely-on-memory-too-much`) — state that the user recognises from visual pattern rather than recalling what an indicator means; in high-consequence contexts this is a safety standard, not a usability preference
- Process mimic — a representation of the physical process (vessels, valves, feeders, flow paths) on which state is shown where the equipment is, rather than in a separate list; the mechanism for process-state recognition (Gericke)
- Symptom-versus-state communication — the distinction between an interface that exposes symptoms (a list of alarms and codes) and one that explains the state that produced them; exposing symptoms forces interpretation and invites misreading a normal condition as a fault (Gericke)
- Spatial consistency / layout stability — the principle that state indicators must not shift position across view transitions; spatial memory is the mechanism that enables glance readability, and layout instability destroys it
- State hierarchy — the organisation of state information by importance; primary state (always visible, highest priority), secondary state (visible in context), tertiary state (accessible but not intrusive)
- State aggregation — combining multiple component states into a single coherent system state display (Torqeedo: propulsion + battery + generation = one unified energy state view)
- Sensor cadence — the update interval of a data source; when multiple sources update at different rates, the display must synchronise them without creating instability
- Mode change / mode indicator — the moment when the system transitions between operational modes; a specific high-risk moment for state visibility failure
- Ambient awareness — maintaining awareness of system state without directed attention; the operational requirement in many complex environments
- State transition — the interface's behaviour when the system moves from one state to another; as important to design as the states themselves

---

## Evidence to draw on

### Torqeedo maritime HMI (state aggregation — strongest measured outcome)
- The central design problem: a hybrid electric vessel integrates propulsion motors, battery banks (40–200 kWh), generators, auxiliary loads, and conversion units. Each is a separate system with its own state. Each updates at a different rate. The captain's question is not the state of each component but the state of the vessel: how much energy do I have, how am I consuming it, what capacity remains?
- The design challenge: presenting multiple sensor systems updating at different rates creates a display that reads as unstable — values changing at different moments, status indicators flickering. The resolution was a grid structure that synchronises competing update cadences into a unified display rhythm. Captains perceive one coherent system, not three competing data streams.
- **50% faster energy state identification — new interface vs. legacy. Controlled environment experiment, 24 subjects. Directly measured.**
- **Glance reduction during manoeuvres — tasks previously requiring multiple screen transitions now confirmable with a single glance. Measured via eye tracking, 7 subjects, during actual sea trials.**
- **All 15 professional captains rated the new interface as significantly better. Participant-reported, structured feedback.**
- State hierarchy explicitly designed: primary (vessel energy state and range), secondary (component-level breakdown available on demand), tertiary (full telemetry accessible but not surfaced by default). The hierarchy allows captains to maintain ambient awareness of vessel state without monitoring every component.

### Cox Marine cluster displays (tile architecture — state coherence across configurations)
- The configuration range spans 1 engine to 6 engines across different vessel types (fast patrol craft, racing boats, workboats). The state communication challenge: a single-engine display and a six-engine display must share a coherent mental model so captains can read both without relearning the interface.
- The engine tile as the invariant unit: one tile per engine, consistent spatial arrangement of state information within each tile regardless of configuration. When the configuration has 6 engines, there are 6 tiles; when it has 1, there is 1. The state reading logic doesn't change.
- Multi-engine fault scenario testing during Concept Convergence: the test revealed that several layout candidates made fault presence visible at the tile level but did not direct attention to the priority engine in a multi-engine fault condition. The state hierarchy within and across tiles had to communicate: something is wrong, and this is where.
- Fault-summary area: a dedicated area surfacing the highest-priority fault condition across all tiles. Captains can identify the priority fault without scanning all tiles individually.
- Military night vision mode: absolute constraint — all state communication must remain legible under night vision goggles, which require specific luminance and contrast ranges that eliminate most standard interface choices.

### Kardion MCS Controller (layout stability as clinical state standard)
- The layout stability standard is the single most specific state visibility requirement in the portfolio: no element shifts position across any view transition. This is Creative Navy's own standard, above the IEC 62366-1 consistency requirement.
- The clinical rationale: surgeons build spatial memory for critical state indicators during a procedure. They depend on that memory when the clinical situation requires rapid response — the blood flow value must be in the same position it was a moment ago, in the same position it was at the start of the procedure. If it has moved, spatial memory fails and active search begins.
- This standard shaped 34 directions of exploration for the standard view — each candidate was eliminated if any element's position changed across the system's view transitions. The constraint was absolute.
- State hierarchy: primary state (device operational status; the min/max flow visualisation that the standard view is built around), secondary state (parameter detail accessible from the standard view), tertiary state (alarm history, configuration). The hierarchy is spatial and visual — not tabbed sections but a layered architecture on a single screen.
- **FDA approval: design passed evaluation as submitted, no design changes required.** The state hierarchy and layout stability contributed to the regulatory review satisfying the identified use-related hazards related to misinterpretation of device state.

### deSoutter Medical / Zethon (recognition over recall in operating theatre conditions)
- The operating theatre is the state visibility stress test: variable overhead lighting, gloved hands, divided attention, primary focus on surgical field. State indicators must be recognisable in a fraction of a second under these conditions.
- The most common failure in competitive benchmarking: colour as the primary state indicator. Under variable theatre lighting — surgical headlights repositioned, overhead field illumination adjusted, different theatre setups — colour coding is unreliable. Most of the 6 benchmarked comparable devices relied primarily on colour.
- Resolution: redundant non-colour cues. Every critical state communicated through spatial position + icon form + colour simultaneously. The failure of any single channel under theatre conditions does not remove the signal.
- The recognition standard: a surgeon looking at the device must be able to confirm the operating state without reading, without recalling what an indicator means, and without taking attention from the patient for more than a brief glance.
- 8 surgeons in structured review sessions confirmed state verification reduced to brief glance recognition. **Surgeon-reported from design review sessions, not post-deployment measurement.**

### Elsner Elektronik (multi-zone and fault state for non-technical users)
- 54 countries; users range from tech-savvy professionals to elderly consumers with limited technical background. State communication must function across this full range without requiring interpretation.
- The multi-zone state display challenge: a single controller managing heating, cooling, lighting, and blinds across multiple rooms; the state of each system must be visible without requiring navigation between views.
- Sensor fault states: a non-technical occupant encountering a sensor fault must be able to understand that something is wrong and that they need to call an engineer, without needing to understand what a sensor fault is or what it means for the broader system. The state communication calibrates the information precisely for that audience.
- Dual-priority alert system: routine notifications (sensor out of preferred range) distinguished visually and behaviourally from critical notifications (complete sensor failure, safety-relevant state change). The hierarchy prevents alert fatigue from degrading the urgency of genuinely critical states.

### Triopsis workforce management (state hierarchy for schedulers under operational pressure)
- Schedulers managing workforce interventions across a live fleet need ambient awareness of fleet state without monitoring every job individually. The interface must surface exceptions — jobs at risk, conflicts developing, incomplete assignments — without requiring active scanning.
- Predictive conflict indicators: future scheduling problems made visible before they become present crises. State communication for an event that hasn't happened yet but is deterministically approaching — a form of state communication with no close parallel in standard software.
- The state hierarchy within the scheduler view was defined by criticality: jobs requiring immediate action (state: exception, conflict, overdue), jobs requiring monitoring (state: in progress, near deadline), jobs in normal state (backgrounded). The visual hierarchy was derived from this operational hierarchy, not from visual interest.
- Field technician job state: technicians in the field need to know what state their current job is in and what is next. The state communication for field use had to function under outdoor conditions — sunlight, gloves, brief glances.

### Gericke industrial HMI (process-state communication on a live mimic — measured outcome)
- The central state communication problem: the legacy Easydos Pro interface exposed *symptoms* — alarm lists, raw error codes, scattered parameters — but never showed *state*. Operators could not reliably tell whether the process was healthy, so under ambiguity they stopped or overrode healthy equipment precautionarily. State communication had to move from a symptom list to a recognisable picture of the process.
- The mechanism is the process mimic: a live representation of the physical process (the twin-vessel conveying schematic, the feeders, the flow paths) on which state is shown where the equipment is, with failed components highlighted directly on the diagram — the brief's "engine parts that have failed light up in the graphic" — replacing raw error codes. State is read off the picture of the plant, not reconstructed from a list.
- A root-cause alarm hierarchy organises the state of abnormal conditions: secondary alarms are collapsed beneath their originating event, and probable cause is indicated rather than a flat list of effects. This is state hierarchy applied to faults — the conveying-blockage example highlights "Valve V12 failed to reach open position — probable root cause of 6 active alarms" directly on the process path.
- The clearest illustration of symptom-versus-state communication: a normal feeder refill cycle previously surfaced as a cluster of alarms with no indication of which mattered, and operators read it as a fault. The redesigned mimic shows the feeder in "Refill Cycle — temporary deviation expected — no operator action required," so the normal state is recognised as normal.
- A three-tier progressive-complexity model governs how much state detail each role meets: operators see operational state first and drill to diagnostic and engineering detail only as the situation requires — ambient awareness of process health for operators, deeper component state for maintenance and engineers.
- **Fault-diagnosis time fell by roughly two-thirds at every site (24 → 8, 38 → 12, 68 → 20 min) and repeat alarms more than halved (42% → 18%, 58% → 28%, 73% → 35%). Client-measured, three sites described by type and geography, within a confirmed single-variable window.** Faster diagnosis is the operational signature of state being legible; the repeat-alarm reduction is the signature of the alarm-state hierarchy working.
- **Evidence basis: client-measured by Gericke (not Creative Navy-measured), confirmed single-variable window; the refill and valve illustrations are Creative Navy reconstructions of the redesign, not logged incidents.** Gericke is not a regulated device; it operates in GMP environments (GAMP 5 relevant) and the validation boundary is the manufacturer's.

### The industrial engagement (one accent colour carrying six meanings — and the seven-state answer)
- The client is **a European industrial automation vendor whose process control software coordinates machining cells**. **The failure findings are what Creative Navy's expert review found in that system — never a general claim about industrial software.**
- The failure pattern: the platform's single accent colour carried six meanings at once — brand, primary action, selected row, active filter, current location, and error (E19); a storage tile showed a green *transporting* header band above a solid red *selected* icon, with four states encoded by header colour alone at ~10px with no legend (E20); in the alarm list, severity was conveyed by a leading icon alone — no text, no row tint (E32).
- The response: a seven-state status taxonomy — ready, warning, processing, done, error, transport, end-of-life — each carrying a distinct hue **plus** text label **plus** icon (E36).
- The operational reason, from field observation: learning a machine's state meant walking to it, and overhead stack lights existed because no screen was readable across the hall (E10). **The cell overview is the digital equivalent of the stack light.**

### AIT heat pump controller (widget status for a knob-driven display)
- AIT, a European manufacturer of residential and commercial heat pumps, may be named.
- The widget status set (A40, A21): **in focus** — selected by the knob — as a black outline; **mode active** as a flashing icon; and a dedicated icon for **mode queued** — the heat pump being asked for a mode while running another. Only one heat-generating mode runs at a time; between one and seven modes may be installed, and most installations are heating and hot water only.
- The start-up self-test screen reports which internal boards, inverters and fans the controller has detected — AIT's own analogy is a PC BIOS screen. It cannot be skipped, only hidden, and a route back to it had to be designed (A24).
- The system overview was rebuilt as widgets consistent with the home screen, with the heat pump illustration replaced by an abstract symbol so one icon covers every unit type (A56). The refrigerant-circuit diagram is labelled with temperatures rather than pressures — pressure is ambiguous and temperature is what an installer reads — with the full value table behind an info button (A55).
- **Design reasoning only: nothing in the AIT engagement was tested with users (A15).**

### Streetec kntrl 2 (which of two true values to show)
- Streetec GmbH and the product, kntrl 2, may be named.
- S41 is the question itself: which of two true values to show, when law mandates one and utility favours the other — German law requires bar at all times, but a customer who has paid for height sensors wants percentage. Three iterations were explored. Resolved as equal-prominence percentage with de-emphasised bar on the screens where both are needed, percentage only when editing a preset, bar when the system is regulating or has finished — and both in manual mode, because the user is working toward a specific height at a specific pressure. **The answer changes with what the user is doing.**

### The MDU ship motion monitor (which value represents the state)
- The product may be named — the MDU; the manufacturer is not named. **The whole product is state visibility and nothing else, which makes this the strongest single body of evidence on the page.**
- The question of which value represents the state: the vessel illustration rotates on the 20-minute rolling average — trim and list — not on the instantaneous angle, because animating the live angle *"will just be too busy"* (M37). **Creative Navy put the cost of that choice on the record: under an alarm, the vessel image will not look like a dangerous situation, because it is showing the average.** The decision stood, with the live value carried by the arrows instead.
- What replaces the live number (M38): a light arrow for current position, two dark arrows for the rolling minimum and maximum which the current value pushes outward and which retreat as the window rolls, and a shaded band between them — distance from the threshold readable without reading a number.
- The removal that forces the rest: the live "Now" value deleted from both cards because a digit updating every second adds attention cost rather than information (M39); the alarm consequently binds to the rolling maximum and minimum, which gives it a precise meaning — at some point in the last twenty minutes this vessel was outside its limits (M41).
- Close with the status bar reduced to a logo and an alarm count, green with none and red with any, after ship name and clock were rejected as information the reader already has or cannot use (M49).

### Assemblio (a state that exists in the data and nowhere in the interface)
- Assemblio GmbH and both products may be named.
- **N98 is the purer instance**: a system that maintains a synchronisation relationship between two products and never shows whether that relationship is currently satisfied — a state that exists in the data, matters to the user, and has no representation anywhere in the interface. It surfaced because Creative Navy asked what the planner sees in a state nobody had described; the client confirmed the deliberate-desync case was acceptable and realised, in answering, that the product does not indicate anywhere whether an assembly plan is in or out of sync.
- The second instance (N77, N51): the progress of a long asynchronous job attached to the object it concerns rather than to a transient global notification — upload handled as a placeholder card with a cancel action, because files can exceed 1 GB and several can process in parallel, so progress belongs on the card for the product it concerns. The inherited behaviour reported asynchronous work in snack bars with no reference to which product each concerned.
- A product state that changes what the primary action is called (N21, N84): products move Draft → In Review → Approved, and while a product is in review, "Open assembly plan" becomes "View assembly plan", signalling read-only **[client-requested]**.

### Topera (status designed to be interrogable — concept design, nothing built)
- Topera may be named; it is a **concept design** grounded in the DIN 69901 series, and **nothing has been built — every sentence must stay true of a system that does not exist**.
- Warnings were designed to be interrogable in place: a warning indicator in the project table carries a tooltip naming the specific condition (T45). Plan, actual and forecast dates are kept structurally separate — a plan block and a separately editable, explicitly saved actual block (T52); **the parallel with the industrial engagement's separation of measured values from operator offsets may be drawn at principle level only**. Read-only state is shown on the item rather than discovered on interaction (T53). Critical-path exposure was designed into the structural view as well as the timeline (T54).

### Egma Order (three layers of disclosure over one production record)
- **Egma Order**, Egma's B2B lens ordering platform.
- G49: eleven manufacturing steps resolved into three headline groups — Order Processed, In Production, Delivery — with the current sub-status on hover and the full breakdown on click. Three layers of disclosure over one production record, so the common question is answered at a glance and the detailed one is still reachable. **The disclosure mechanism was the client's proposal; Creative Navy resolved the headline set.**

### KISPE Space common space operating picture (information state — what is known about a reading)
- KISPE Space, a UK space systems engineering company. No speech from this engagement is quoted or reported.
- **The page's other entries concern device or process state: what the machine is doing. KISPE concerns information state: what is known about a reading, and how well.**
- Status is seven independent dimensions, not one scale (K55): source transport; asset access; asset delivery; freshness; origin; operational condition — and only where the source semantics actually support that classification; local change state. The rejected alternative is named every time: one green-to-red health score, which is compact and would make identical colours carry conflicting meanings across domains.
- Four prohibited shortcuts, stated explicitly (K56): grey is not necessarily offline; red is not necessarily inaccurate; an old observation is not automatically false; a nominal coverage footprint is not proof that a particular terminal is connected.
- Freshness is the outcome of a rule, not a confidence score (K58): age is computed from a record's own measurement time against its own configured policy, and a stale record may be a perfectly correct historical observation — the interface does not relabel it as false.
- **This is a specification reasoned from a synthetic fixture; nothing was executed or validated (K99), and the product was built without a design-fidelity comparison.**

### Schone Airspace Group Mission Control (transaction state — an instruction in flight)
- The client is named Schone Airspace Group. No speech from this engagement is quoted or reported.
- **Schone adds transaction state: the condition of an instruction in flight, which is neither a property of the machine nor of a datum but of a request that exists between them and has a lifetime.**
- A seven-state command transaction model (D85): ready to request, request sent, awaiting response, command acknowledged, state observed, request rejected, response unknown — each with its own required source evidence and its own prohibited inference, recorded side by side. Acknowledgement does not mean the intended mode has been observed; rejection cannot be inferred from silence. Rejected alternatives: a success toast on click, and a spinner until the mode changes. The accepted cost: more command states require precise copy and event matching, in exchange for less ambiguity about the outcome of each action.
- A transaction keeps the aircraft it was dispatched against (D86): a pending request keeps its original recipient, action and request identifier, and a new target does not rewrite history.
- Pair with D88: control link condition and telemetry freshness as independent fields, a value that has stopped updating keeping its last value alongside its age.

### Raymarine next-generation fixed-mount VHF (requested versus effective — a distinction no other entry makes)
- The client is named Raymarine; the new radio's name may not be used. No speech from this engagement is quoted or reported.
- Raymarine's transaction state overlaps with Schone's and is not a discovery: the difference worth keeping is that Schone's is a command whose execution is observed, while Raymarine's is a **protocol transaction whose states are defined outside the product and which the screen may only relay** (R123): six distinct calling states with language fixed for each, where a missing acknowledgement and a failure to transmit are different outcomes with different recovery paths, and a routine timeout never escalates into a distress call.
- **The genuinely new contribution is the requested-versus-effective distinction.** The system holds two true values and must show the operative one: requested transmit power against effective transmit power — the display always shows the effective one, and a blocked request leaves the previous value intact and explains the channel restriction (R113); and the selected working channel against the channel a scan or watch mode is currently sampling — a second label identifies the frequency actually being heard, because monitoring must not suggest an automatic change to manual tuning (R112).
- Pair with R110: a rejected channel request is rejected atomically, with no retune queued to apply when the restriction lifts, because a delayed change would arrive after the operator had moved on.
- **Carry the measured evidence**: three of eight read a generic success surface correctly while five interpreted a generic call-sent message as meaning the other vessel had responded; eight of eight read the explicit transaction states correctly (R75). **Bench prototype sessions, eight participants, a fixed scenario fixture — not radio performance, not outcomes at sea.**

### The handheld C2 engagement (commitment state — distinct from all of the above)
- The client is **a European manufacturer of uncrewed systems, including one-way effectors, and the tactical command-and-control software that operates them**. The engagement covered interface structure, task behaviour, information priority and the clarity of operator control; it did not extend to autonomy, control algorithms, the datalink, the effector, targeting logic, or any certification or weapons-review activity. **Creative Navy designed the surface through which a human supervises the system; it did not design the system.** No speech is quoted or reported. The deliverables were work Creative Navy **led and co-authored** with the client's design team.
- **Lead with H73, stated as a rule in the source rather than inferred — the page's clearest statement of the general principle: a requested state must not visually replace a confirmed state before the vehicle reports the result.**
- The state separations, stated as rules (H72): vehicle status, mission segment, guidance mode, armament state, command state, system health and alert priority are related and must not be treated as interchangeable — vehicle status describes what the vehicle is doing; mission segment describes where the mission is; health and alerts describe what is wrong.
- Armament state as five explicit values: safe, armed, change pending, unavailable, unknown (H74). Command state as seven explicit values: requested, sending, awaiting acknowledgement, accepted, rejected, timed out, resulting state confirmed — **followed by the instruction to use only states the technical system can actually determine** (H75).
- **H79 is a rule the page does not otherwise make**: information serving several functions must not become several independent interface objects; each fact has one authoritative value, surfaced contextually wherever it is needed.
- **And H77**: a value is useful only in relation — a power percentage does not establish whether recovery is viable, because what the operator needs is the relationship between endurance remaining, time to recovery and expected reserve.

### Maritime traffic software portfolio (evidence state — and the refused confidence score)
- The client is **a European vendor of maritime traffic monitoring, inland navigation and communications software for port authorities, coastal administrations and waterway operators**. No speech from this engagement is quoted or reported.
- **This engagement adds evidence state, distinct from the four state classes above.** A track carries a source, an observation time and a receipt time, and the three may differ (W68 — eight distinctions the component system is required to keep apart: vessel and track; track and observation; associated and verified; event time and receipt time; traffic alert and equipment fault; acknowledge and resolve; live and replay; radio resource and transmission). An association between an AIS identity and a radar track is resolved, unresolved, changed or unknown, and the interface says which (W52). A retained last-known position and a current observation are given different treatments, because the legacy interface gave them the same one (W43).
- **Lead the entry with W53, the refused confidence score — the page's clearest statement that a status display's job is to report what the system knows rather than to resolve it for the reader.** A numeric association-confidence badge was explored and was attractive because it would compress uncertainty into one familiar control. The client's engineering could not supply a calibrated, operationally defensible confidence figure, so the interface was not permitted to display one; the design states the association unresolved instead, and the rule entered the specification: the interface does not synthesise an association confidence score, a source time or an authorisation decision, and missing values appear as unknown or not available.
- **One distinction the page does not otherwise make, from W43, and it is a general rule: an absent state and a healthy state are different, and an equipment view with no data must not read as an equipment view with no faults.**
- **Carry the measured evidence with its full framing**: vessel identification — legacy median first answer 61.5 seconds, prototype 35.5 seconds, 42.3% lower; correct first answers 6 of 8, then 8 of 8; all eight participants answered sooner on the prototype (W85). **This result is Creative Navy-measured under controlled conditions. Eight participants completed matched tasks using sanitised training scenarios on a design prototype, not a production installation. Six of the eight had taken part in earlier research or testing. The time measure is time to a first submitted answer regardless of whether that answer was correct, not time to successful completion. The study reports no significance test, no confidence interval and no power calculation, and states that its percentages must not be combined with the other tasks' into one figure.**

## What this page must not claim

- The state classes stay distinct: device/process state (the existing entries), information state (KISPE), transaction state (Schone), protocol transaction state (Raymarine), commitment state (handheld C2), evidence state (maritime VTS). Never blend their evidence in a sentence or let one lend weight to another.
- KISPE: specification, never completed testing (K99); no research or validation claim (K26); no shipped-as-designed claim.
- Schone: conformance results are not outcomes; the product is in test; nothing measured in flight; no quotation or reported speech.
- Raymarine: no safety, rescue or collision outcome; no type-approval, certification or conformity credential; no field, glove, lighting or vibration claim (R90); no statistical claim from eight participants; the terms *performance in reality* and *competitive vector* are forbidden on any page carrying Raymarine.
- Handheld C2: no quotation or reported speech; no claim the design prevents error; status is "was built" and nothing more; no operational or workload figure (H116).
- Maritime VTS: never average the three study percentages or write a combined headline; never "eliminated operator error" — all eight answered the four prototype scenarios correctly in the prescribed exercise, and the sentence stops there; never convert faster into better in one clause; never attach an operational consequence; no "shipped as designed" (W98).
- AIT and the MDU: design reasoning only — nothing tested with users (A15, M27). The MDU's day, dusk and night display modes, where mentioned, are shipped features, never "ECDIS-compliant colour modes".
- Assemblio: client-stated context, no outcomes, no audit framing (N15).
- Topera: nothing exists; no outcome, no user, no client decision records (T19, T20).
- Egma: no post-launch measurement of any kind.
