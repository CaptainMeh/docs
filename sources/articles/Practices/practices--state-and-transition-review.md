# `/practices/state-and-transition-review`

---

## What the practice is

Every complex system exists in multiple operational states — nominal states, fault states, configuration modes, processing states, degraded modes — and transitions between them continuously during use. The state-and-transition review is a structured examination of two things: whether each state is communicated clearly enough for users to understand what the system is doing without active interpretation, and whether each transition between states is handled in a way that maintains that clarity rather than disrupting it.

The practice distinguishes between:

**State visibility failures** — states that users cannot read accurately: indicators that require interpretation rather than recognition, status information buried where users don't scan, or state changes so subtle that users continue acting on a prior assumption.

**Transition failures** — the moments when the system moves from one state to another: view changes that shift the spatial position of elements users were relying on, mode changes that are visually ambiguous, processing transitions (loading, calculating, updating) that leave users uncertain whether the system is working or waiting for input.

Both categories are evaluated against the conditions of actual use — not controlled viewing conditions. A state indicator that is readable on a desktop in good lighting may be unreadable on a helm display in rain, or on a surgical instrument interface under variable theatre lighting, or on a calibration device read from two metres during movement.

---

## What the review examines

**State catalogue** — a complete inventory of every system state: nominal operating states, degraded modes, fault states, configuration states, processing states, alarm states. In complex systems, this catalogue is typically larger than stakeholders expect because many states were added incrementally without a unified state architecture.

**Transition map** — for each transition between states: what triggers it, what visual change occurs, whether the user receives notification or must infer the change, and whether any element changes spatial position as part of the transition.

**Spatial consistency audit** — a systematic check of whether any element changes position across view transitions. Spatial memory is the mechanism that enables glance readability; any element that shifts position across a transition requires users to relocate it rather than rely on learned position. In high-consequence contexts, this is not a minor inconvenience — it is a design failure with operational consequences.

**Mode change identification** — specific identification of the transitions that constitute mode changes: states where the system's behaviour changes fundamentally rather than just its display. Mode changes are the highest-risk transitions because users who haven't registered the mode change will interpret system behaviour incorrectly.

**Operating condition evaluation** — each significant state and transition evaluated under the conditions of actual use: the visual environment the user is in, the attentional load they are carrying, the physical constraints they are operating under.

---

## When it is used

During Sandbox Experiments when reviewing an existing system — the state-and-transition review is part of the evidence base for understanding what the system is doing before any design decisions are made.

During Iterative System Building when reviewing proposed designs — the review is applied to prototypes to identify state and transition failures before they are implemented.

In regulated medical device contexts, the review has direct alignment with IEC 62366-1 requirements for mode change identification — the standard requires that mode changes be clearly communicated and that foreseeable misuse arising from mode confusion be addressed in the design.

## Evidence from engagements

**Kardion MCS Controller** — The state-and-transition review produced the engagement's most consequential design standard: no element shifts position across any view transition. This is Creative Navy's own standard, above the IEC 62366-1 consistency requirement. The clinical rationale emerged from the review: surgeons build spatial memory for critical state indicators during procedures and depend on that memory when the clinical situation demands rapid response. The standard view, the alarm overlay, the parameter adjustment overlay — the review examined every transition between these views and identified which element positions were being relied upon by each user type. Any element that moved across a transition was redesigned or removed. **The FDA approval outcome (design passed evaluation as submitted, no design changes required) reflects in part a state architecture that the review established from the start.**

**deSoutter Medical / Zethon** — The state-and-transition review in the operating theatre context specifically examined mode change communication under divided attention. The review identified the primary failure across competitor devices: colour as the sole differentiator between states. Variable theatre lighting renders colour-only state communication unreliable. **Most of the 6 benchmarked comparable devices** relied primarily on colour for critical state indicators. The review produced the requirement for redundant cues (spatial position + icon form + colour) that addressed this failure. The review also identified activation state recognition as the highest-risk transition — the moment when the instrument transitions from ready state to active use — and specified the recognition standard: confirmable in a fraction of a second under divided attention, gloved hands, and variable lighting.

**Torqeedo maritime HMI** — The review identified the central design problem: propulsion motors, battery banks, and generators update their telemetry at different rates. Presenting them without a synchronisation architecture creates a display that reads as unstable — values changing at different moments, status flickering — during active vessel operation. The review mapped all sensor update cadences and identified the transitions that were creating visual instability. This produced the requirement for a grid structure that synchronises competing cadences into a unified display rhythm, eliminating the transition instability rather than managing it.

**Elsner Elektronik / Cala Touch KNX** — The review of the existing interface examined three categories of state communication failure: sensor fault states (the display when a sensor is in fault), calibration drift states (how the display behaves when sensor readings drift out of calibration range), and the relationship between animation timing and firmware update cycles. The last of these was a transition-level finding: the firmware updated thermal values at a specific cycle; the animation timing had to be aligned to those cycles so that visual state changes never drifted out of sync with actual system state. Without this alignment, the display would show a state that the system had already left — a transition failure invisible under normal conditions and apparent under edge conditions.

**Cox Marine cluster displays** — The review specifically examined how fault state transitions communicated across multi-engine configurations. The finding: a design that made fault presence visible at the tile level but did not direct attention to the priority engine in a multi-engine fault condition was failing the transition requirement. A fault condition is a state; the transition into that state must do more than change a colour — it must redirect the user's attention to the right location. The dedicated fault-summary area and per-tile alarm state highlighting emerged from this review.

**Tetra/Prism property compliance** — The review of the existing mobile app identified a transition failure as the primary adoption barrier: when the app launched, it entered a downloading state (downloading the entire property portfolio) that appeared visually like normal app loading but lasted up to 10 minutes. Users couldn't distinguish between "loading" and "broken" — a transition state failure where the system's processing state was invisible. The design solution (property selection at launch, limiting download scope) emerged from identifying this as a transition communication failure rather than a technical loading problem.

**KISPE Space (a UK space systems engineering company)** — Six state models and eight cross-module regression checks, covering area confirmation and query lineage; imagery catalogue and asset retrieval; provider reachability and device observations; local annotation synchronisation; saved live view versus frozen briefing; and notification interaction (K11). **The query-lineage model is the distinctive one — a race condition specified as an interaction contract rather than left to engineering**: every area-scoped request carries the area identity, a geometry signature, the filter set, the temporal perspective and a generation time, and a late response from a superseded request may not populate the current results — if a user starts a search, changes the area, and the first search returns last, the older results do not appear under the newer area's label. **The accepted cost was named: this requires request lineage and cancellation semantics, not just a loading spinner** (K45). **The state models and regression checks are specifications; the tests were specified, not executed. No quotation marks and no reported speech anywhere KISPE appears.**

**Oceaneering (hospital dispatch panel; nothing beyond the client name may be named)** — A worked example of enumerating states with the people who operate them. The send-station states, enumerated from the field: nothing on the station, a cart on it, a dispatched cart — and no others — with equivalents for receive and for combined stations. The resolved scheme carries a stated logic: one colour for sending, one for receiving, each flashing when an action is required and steady when it is not, red reserved exclusively for errors, and seven station statuses each carrying colour plus a directional icon plus the role letter, with a legend reachable from the panel (O62). Two designed states were then deleted on field evidence: a disabled-station state, after both sites reported never having disabled one, and a grey fill for empty stations, resolved instead to a transparent card with a coloured outline, on the grounds that fewer colours mean fewer things to learn (O67). **Oceaneering client positions are reported speech attributed to a role, never quoted.**

**Raymarine (next-generation fixed-mount VHF; the new radio's name is never used)** — **Eight state axes that vary independently, explicitly not one mode enumeration**: voice radio state, display context, calling transaction, AIS data quality, positioning, safety incident, interruption and chartplotter link. An operator can be on an AIS plot, awaiting an acknowledgement to a call sent two minutes earlier, holding no valid position fix, running an active man-overboard incident and disconnected from the chartplotter — simultaneously, with none of those facts implied by any of the others. **The method contribution is the refusal to collapse them**, and the forty-three exception records are what that refusal costs and buys. The governing statement: a current screen is not a system state, and the interface is a state interpreter rather than the source of truth for radio outcomes (R133). **No quotation marks and no reported speech anywhere Raymarine appears.**

**Schone Airspace Group (uncrewed aircraft Mission Control)** — Twelve operational state models covering 58 defined states — workspaces, readiness, control link, telemetry, eligibility, commands, flight mode, alerts, fleet selection, camera, streaming, review — with the note the source material itself carries: **the counts describe distinct interface conditions, not aircraft, screens, alerts or protocol events** (D13). The command transaction model is the distinctive one, because it is a state machine whose transitions are gated on evidence arriving from outside the system rather than on user action: seven states — ready to request, request sent, awaiting response, command acknowledged, state observed, request rejected, response unknown — each with its own required source evidence and its own prohibited inference recorded side by side. Acknowledgement does not mean the intended mode has been observed; state observed cannot be inferred from acknowledgement alone; rejection cannot be inferred from silence. Rejected alternatives: a success toast on click, and a spinner until the mode changes. **The accepted cost: more command states require precise copy and event matching, in exchange for less ambiguity about the outcome of each action** (D85). **No quotation marks and no reported speech anywhere Schone appears.**

**Maritime VTS (a European vendor of maritime traffic monitoring, inland navigation and communications software for port authorities, coastal administrations and waterway operators)** — The definitional discipline comes before the count: **a state was defined before it was counted — a material state represents a change in meaning, available action, source validity, ownership, mode or failure response; theme, density and ordinary hover decoration are not states and are not multiplied into the inventory** (W64). That definition is the reason 91 is a defensible number, and the definition matters more than the count. Eight distinctions the component system is required to keep apart: vessel and track; track and observation; associated and verified; event time and receipt time; traffic alert and equipment fault; acknowledge and resolve; live and replay; radio resource and transmission (W68). Then the mode decision: replay as a persistent property of the workspace that every linked panel inherits, rather than a value in a control — a historical overlay on a live-styled map was rejected because links from events to tracks created ambiguity between seeking within a recording and returning to live, and a detached replay window was rejected because it broke context; the selected model marks the entire relevant workspace as historical, with recording time, coverage and gaps shown, linked inspectors inheriting the same time context, and Return to Live as a deliberate action (W56). Its evidence: replay recognition, untimed — correct initial mode identification 5 of 8 in the legacy condition, 8 of 8 in the prototype, with three participants misidentifying the legacy state and the task scored only for whether the participant recognised that the picture was historical (W87). **This result is Creative Navy-measured under controlled conditions: eight professional VTS operators and supervisors on a design prototype with sanitised training scenarios, six of the eight with earlier programme exposure, not a production installation. Never convert 8 of 8 into "eliminated operator error" or any general property, and never attach an operational consequence. No quotation marks and no reported speech anywhere this engagement appears.**

**The industrial engagement (a European industrial automation vendor whose process control software coordinates machining cells)** — A state-visibility audit finding, phrased as what the review found in that system: a storage tile showed a green *transporting* header band above a solid red *selected* icon; the only other selection cue was a near-imperceptible border change; four states were encoded by header colour alone at roughly 10px with no legend (E20). The designed response: a status timeline component distinguishing future, current and completed steps, marking automatic versus manual transitions, surfacing preconditions on hover, defining reversion behaviour, confining touch targets to the cards — delivered as documentation plus prototype, marked ready for development (E39).

**Streetec kntrl 2** — Immediate versus saved change: manual adjustments execute immediately; preset edits must be explicitly saved. Two different mental models in one interface, deliberately separated (S42).

**AIT (a European manufacturer of residential and commercial heat pumps)** — A defined set of widget status indicators: in focus (selected by the knob) is a black outline; mode active is a flashing icon; mode queued — the heat pump being asked for a mode while running another — carries its own icon (A40). The underlying mode model: heating, cooling, domestic hot water, pool, photovoltaics and ventilation; only one heat-generating mode runs at a time, photovoltaics and ventilation can run alongside one, between one and seven modes may be installed, and most installations are heating and hot water only (A21). A start-up self-test screen lists the internal boards, inverters and fans the controller has detected — AIT's own analogy is a PC BIOS screen; it cannot be skipped, only hidden, if components are not found within the window the controller enters a special operating mode, and a route back to the self-test had to be designed (A24). Leaving commissioning part-way produces an explicit save progress / discard / return choice rather than silent loss (A52). **These are design reasoning; nothing in the AIT engagement was tested with users.**

**The MDU (ship motion monitoring; the manufacturer is not named)** — The alarm state machine: flashing red until acknowledged, solid red after *Acknowledge* ("I have seen it"), self-clearing when the condition is no longer present (M42), with a separate path for an alarm that clears before anyone acknowledges it — retained in the log behind a count badge with an acknowledge-all available (M44). And the distinction between an instantaneous state and a windowed one, made explicit: the alarm does not bind to the live value, which leaves the alarm band seconds after entering it, but to the rolling maximum and minimum — an alarm means the vessel was outside its threshold at some point within the last twenty minutes (M41).

**Assemblio (Stuttgart; Composer and Smart Viewer)** — Two state gaps surfaced by questions rather than research, which is what this practice is for. Creative Navy asked what happens when two products are in a sync loop, a change is made to one, and the other is deliberately left unsynchronised; the client confirmed the state was acceptable and then realised, in answering, that **the product does not indicate anywhere whether an assembly plan is in or out of sync** — a planner would have to open the product to find out. This was not a known gap before the question (N98). And a transition whose semantics had to be established by direct question, because the word "sync" suggests something other than what it does: it is an override, not a merge — the branches are never merged back, synchronising overrides the target's existing state, and synchronisation is always manual, never automatic, because the change can be substantial enough to be destructive (N91). **Both came from questions put to the client, not from research: Creative Navy conducted no user research of its own on this engagement.**

## What this page must not claim

- No quotation marks and no reported speech for KISPE, Raymarine, Schone or maritime VTS; Oceaneering is reported speech only, never quoted; MDU quotes are cleared and permitted, attributed to role.
- Counts never migrate or merge: KISPE's six state models, Schone's 12 models and 58 states, Raymarine's eight axes and forty-three exception records, and the VTS 91 states are different units from different clients — never place two inventories in one sentence without naming the unit each time.
- KISPE's regression checks are specified, not executed; Schone's state counts are interface conditions, not aircraft or events; the VTS replay figure carries its full framing every time.
- No claim that any state architecture prevented an incident or an error; no safety, certification or regulatory credential from any engagement on this page.
- No engagement dates — sequence and duration only.
